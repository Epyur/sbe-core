# Инструкция: слабые места проекта и как их проверять и чинить

Документ по итогам Этапа 1 (auth-service, 2026-08-17) + известные слабости стека.
Структура по каждому пункту: **что** → **как проверить** → **как чинить**.

## A. Серверная часть (auth-service / exim / стек)

### A1. exim: TLS-соединение идёт с `SMTP_SKIP_VERIFY=1`
- **Что:** у exim самоподписанный сертификат `CN=epyur.fvds.ru` **без subjectAltName** —
  Go не может его проверить для `host.docker.internal`, поэтому в `email.go` включён
  `InsecureSkipVerify`. Соединение шифруется, но не аутентифицируется.
- **Как проверить:** `openssl s_client -connect localhost:25 -starttls smtp </dev/null 2>/dev/null | openssl x509 -noout -subject -ext subjectAltName` (на сервере). Пустой subjectAltName → проблема на месте.
- **Как чинить (варианты):** 1) выпустить нормальный сертификат для exim и убрать `SMTP_SKIP_VERIFY=1`;
  2) при постоянном спаме — перейти на внешний SMTP-реле с `SMTP_USER`/`SMTP_PASS` (код поддерживает).

### A2. exim: sender verify требует локального пользователя-отправителя
- **Что:** шаблон ispmanager делает `require verify = sender`; без записи в `/etc/exim4/passwd`
  адрес `noreply@epyur.fvds.ru` не резолвится (`domain missing or malformed in "noreply@"`).
  Добавлена строка `noreply@epyur.fvds.ru:!:65534:65534:/var/mail::0:`.
- **Как проверить:** `exim -bv noreply@epyur.fvds.ru` → должно быть `verified`.
  Если `cannot be resolved` — запись пропала.
- **Как чинить:** пересоздать запись в `/etc/exim4/passwd` (бэкап: `passwd.bak`).
  Осторожно: ispmanager может перегенерировать passwd/конфиг при действиях в панели — проверять после.

### A3. exim: разрешён релей из docker-сети (риск открытого релея)
- **Что:** в `/etc/exim4/relay_from_hosts` добавлено `172.16.0.0/12` — любой контейнер в docker-сетях
  может слать почту на любые домены (потенциальный спам-вектор).
- **Как проверить:** `cat /etc/exim4/relay_from_hosts`; список очереди `exim -bpc` и лог
  `/var/log/exim4/mainlog` на предмет чужих отправителей.
- **Как чинить:** сузить до конкретной compose-сети (например, `172.18.0.0/16` — сеть `internal`),
  либо включить SMTP-аутентификацию и убрать подсеть вовсе.
- **Статус (2026-08-17): ЗАКРЫТО.** Релей сужен с `172.16.0.0/12` до `172.18.0.0/16`
  (фактическая сеть `mailers_internal`), проверено `exim -bh 172.18.0.3` → `250 Accepted`.
  Бэкап: `/etc/exim4/relay_from_hosts.bak2`. При добавлении новых compose-сетей — дополнять файл.

### A4. auth-service: `POST /apps/register` без аутентификации
- **Что:** любой, кто может достучаться до auth-service (через Caddy — публично), может
  зарегистрировать/перезаписать запись приложения (включая `owner_email`).
- **Как проверить:** `curl -s -X POST https://epyur.fvds.ru/apps/register -H 'Content-Type: application/json' -d '{"app_id":"mailer","name":"X"}'` — вернёт `{"ok":true}` без какого-либо секрета.
- **Как чинить:** требовать сервисный секрет при регистрации (заголовок `X-Service-Secret`
  или сверка с существующей записью), либо закрыть `/apps/*` от публичного доступа (allow from internal).
- **Статус (2026-08-17): ЗАКРЫТО.** `authorizedRegister`: мастер-секрет `APPS_REGISTER_SECRET`
  (env) либо совпадение с текущим `service_secret` записи; иначе 403. Новое приложение — только по
  мастер-секрету. `/apps/*` убран из публичного Caddy (остаются `/auth/*` и `/health`).
  Проверено: без секрета 403, неверный 403, существующий секрет ok, мастер ok, публичный `/apps/*` — fallback.

### A5. auth-service: `POST /auth/request-key` без rate-limit (спам по почте)
- **Что:** на каждый запрос генерируется ключ и отправляется письмо; без ограничения частоты
  адрес можно заспамить письмами (повторный `request-key` на чужой email).
- **Как проверить:** серия из 20+ запросов подряд — все примутся и отправят письма.
- **Как чинить:** rate-limit по `email`/`device_id` (напр., Redis-подобный счётчик или
  таблица `requests` с окном), плюс капча в ЦУП при запросе ключа.
- **Статус (2026-08-17): ЗАКРЫТО.** `requestLimitExceeded`: не более `RATE_LIMIT_PER_10MIN`=3 ключей
  за 10 минут на email + не более `MAX_PENDING_KEYS`=5 висящих pending-ключей. Превышение → 429.
  Проверено: req1–3 ok, req4 → `429 too many key requests, try later`.

### A6. auth-service: `/apps/*` и `/auth/devices` доступны через публичный Caddy
- **Что:** маршруты `/auth/*` и `/apps/*` открыты наружу (нужно для ЦУП), но `/apps/register`
  наружу не обязателен.
- **Как проверить:** `curl -s https://epyur.fvds.ru/auth/devices` (без ключа) → 401 (ок),
  но `apps/register` публично вызывается.
- **Как чинить:** оставить публичными только `/auth/*`; `/apps/register` — по внутренней сети
  (в Caddyfile убрать `handle /apps/*` или ограничить source-IP).
- **Статус (2026-08-17): ЧАСТИЧНО ЗАКРЫТО.** `handle /apps/*` удалён из Caddyfile —
  `/apps/register` теперь доступен только во внутренней docker-сети (plugin-services ходят напрямую).
  `/auth/*` остаётся публичным по дизайну (нужен ЦУП и клиентам для активации).

### A7. Общий JWT_SECRET и отсутствие audience/issuer
- **Что:** один `JWT_SECRET` подписывает токены для всех plugin-services; claims не содержат
  `iss`/`aud`, только `app_id`. Компрометация секрета = подделка токена для любого сервиса.
- **Как проверить:** расшифровать payload JWT (base64url) — нет `iss`/`aud`;
  проверить, что plugin-service валидирует только подпись.
- **Как чинить:** добавить `iss: "auth-service"`, `aud: app_id` и валидацию в
  `requirePerm`; ротация `JWT_SECRET` (в `.env` + в БД не хранится, только env).

### A8. SPF/DKIM/DMARC для `epyur.fvds.ru` отсутствуют
- **Что:** домен `fvds.ru` не наш; письма уходят без SPF/DKIM → риск попадания в спам
  и возможность спуфинга отправителя.
- **Как проверить:** письма от `noreply@epyur.fvds.ru` в папке «Спам»; заголовки письма
  (`Authentication-Results`), или онлайн-проверка.
- **Как чинить:** настроить SPF/DKIM на DNS хостера, либо (надёжнее) использовать
  корпоративный SMTP-реле с аутентификацией (`SMTP_USER`/`SMTP_PASS`).

### A9. Portainer: пароль администратора не подтверждён
- **Что:** `process.md` отмечает «админ-пароль задать при первом входе (если ещё не задан)».
- **Как проверить:** `ssh -L 9000:127.0.0.1:9000 root@176.12.69.109` → `http://localhost:9000` —
  требует ли пароль; если требует и не помнишь его — сбросить.
- **Как чинить:** задать пароль (если не задан), либо пересоздать контейнер с новым volume.
- **Статус (2026-08-17): ЗАКРЫТО.** Учётка — **`epyur`** (НЕ admin). Пароль был утерян → сброшен
  через `portainer/helper-reset-password` на volume **`mailers_portainer_data`** (внимание: compose
  даёт префикс `mailers_`, а не `portainer_data`!). После сброса пароль сменён через API
  (`PUT /api/users/1/passwd`), вход проверен. Порт 9000 — только на `127.0.0.1` (bind + nft), снаружи недоступен.
  Новый пароль — у пользователя (при необходимости зафиксировать в гайде).

### A10. Секреты в открытых текстовых документах (process.md / гайд.md)
- **Что:** пароли/токены (root, API_TOKEN, POSTGRES_*, JWT_SECRET и т.п.) лежат в обычных
  markdown-файлах вольта. Если вольт когда-либо синхронизируется/утечёт — секреты утекут.
- **Как проверить:** `grep -rn "password\|secret\|token" *.md`.
- **Как чинить:** вынести секреты из вольта (серверный `.env` + менеджер паролей);
  как минимум — не добавлять новые секреты в md.

### A11. В `yougile-tntn` ~36 ошибок типов, нет тестов/линта
- **Что:** известная плавающая зона: `npx tsc --noEmit` даёт ~36 ошибок, `tsc` в лоб кладёт JS в репозиторий (outDir), `.rules` местами устарел.
- **Как проверить:** `cd yougile-tntn && npx tsc --noEmit` (не `tsc`!).
- **Как чинить:** не добавлять новых ошибок; чистка — отдельной сессией по согласованию.
- **Статус (2026-08-26):** плагин выводится из использования (не обновляется/не поддерживается) — чистка типов не планируется, из поля проверки безопасности исключён.

### A12. Два плагина с id `obsidian-yougile` (`obsidian-yougile/` и `yougile-tntn/`)
- **Что:** путаница, какой плагин реально загружен; раньше `updater` таргетил папку `yougile-tntn`, но дергал плагин по id (сам `updater/` выведен из эксплуатации 2026-08-26).
- **Как проверить:** в Obsidian Настройки → Community plugins → включить/выключить `obsidian-yougile`, смотреть, из какой папки перезагружается код.
- **Как чинить:** привести к одному id/папке (переносим в план Этапа 4/6).

## B. Как быстро проверить стек после изменений

```bash
# на сервере:
cd /opt/mailers
docker compose ps
docker compose exec auth-service wget -qO- http://localhost:3000/health   # {"db":"ok","status":"ok"}
docker compose exec auth-db psql -U auth -d auth -c '\dt'
exim -bv noreply@epyur.fvds.ru                                            # verified
exim -bpc                                                                 # очередь писем
tail -20 /var/log/exim4/mainlog

# с ПК:
curl -s https://epyur.fvds.ru/health
curl -s https://epyur.fvds.ru/api/health
# полный цикл auth: см. скрипты-шаблоны (request-key → письмо → activate → token)
```

## C. Приоритет

1. **Срочно/безопасность:** A9 (пароль Portainer — подтверждён пользователем, порт закрыт), A4 (apps/register — закрыто), A5 (rate-limit — включён), A3 (релей — сужен).
2. **Доставка почты:** A8 (SPF/DKIM или внешний релей), A2 (запись в passwd — держать в гайде).
3. **Архитектура:** A7 (iss/aud, ротация секретов), A1 (сертификат exim).
4. **Гигиена вольта:** A10, A11, A12.

> Замечание: правки по п.п. «фикс» — только после согласования (по правилам проекта запись
> найденных ошибок/отступлений в AGENTS.md делается по явной команде).
